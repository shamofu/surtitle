# AI, audio preparation, and spending

The Rust AI crate owns credentials, immutable inputs, requests, usage accounting, and transcript review. No IPC returns service-account JSON or access tokens. Generated content is labeled so learners can review it against the source. See [Vertex AI setup](vertex-verification.md) for application and CLI instructions.

## Model selection

There is no local model catalog or version allowlist. Settings contain separate, initially unset preferences for transcription, vocabulary, explanations, and translation. **Set up the recommended combination** assigns a selected Transcribe model to transcription and a selected Flash model to the other three purposes. Only unset purposes are initially checked; replacing an existing configuration requires selecting that purpose. **Detailed settings by purpose** and individual jobs allow further changes. Fetch Google publisher suggestions once in Settings to share them across all four purposes; a syntactically valid Gemini ID can also be entered directly. Discovery does not establish that the user's project has access. Changing location or importing another credential invalidates the shared suggestions.

The output limit defaults to an application preset for each purpose: 4,096 tokens for explanations, 8,192 for vocabulary, and 12,288 for transcription or translation. Use **Standard (recommended)** for typical requests, or choose **Custom** to edit the per-request token ceiling in detailed settings. Existing custom values are retained. These presets do not guarantee that every model supports the selected settings or that every response fits the ceiling.

ExecutionConfig freezes the model ID, location, output limit, thinking configuration, and optional price snapshot. PreparedJob also freezes request bodies, media/source revision, settings digest, project, and credential identity. Changing these inputs requires a new quote. No running job changes model automatically.

Choosing a recognizable Transcribe or Flash model pairs it with the corresponding transcription API mode, which remains editable through **How to create subtitles**. The standard Transcribe path uses one VERBATIM request with word timestamps for each prepared audio chunk. Transcribe text is the basis for the resulting transcript; word anchors are validated separately for subtitle timing. **Generate timed subtitle cues** remains available in detailed settings for the general audio adapter. Both use the `generateContent` endpoint. Unsupported combinations fail visibly. No timing failure or VAD disagreement triggers an automatic second request, model switch or paid correction.

## Application workflow

**Transcribe** opens the transcription workspace in the Study page's **Transcript** panel. The transcription action in **More → Prepare subtitles** opens the same workspace; embedded-text extraction, subtitle import and previous editions remain in the source dialog. Transcription defaults to the complete recording, regardless of the current subtitle. Once the duration and configured credentials/model are available, opening this workspace starts local preparation and prepares one quote. **Change range or model** contains the range and execution settings; **Update estimate** refreshes a changed scope. A selected range is expanded to the edges of any existing subtitle it intersects, and the actual range appears in the estimate.

For a priced transcription, review the quote and press **Start transcription**; the button itself approves the displayed scope and reservation. There is no additional quality-consent checkbox. Unpriced work still requires acknowledgement that its price cannot be determined. New transcription approvals include up to two automatic retries per chunk for HTTP 429 only. The quote distinguishes the number of chunks from the maximum number of sends, submitted audio and output tokens, and includes the retry allowance in the maximum reservation. New full-recording, range and re-transcription jobs publish received text into the normal subtitle list while execution continues. Generated text can be replayed, translated, explained and saved as cards without a whole-transcript review or adoption action.

**Set up and return** keeps the request inputs while opening Settings. **Save and return to your request** restores that operation. Unfinished setup can also be resumed later. A queued job's **Open estimate** action reopens approval; expired estimates and changed settings require fresh review. **Resume remaining work** prepares a new approval for unsent or explicitly retried work, retaining already received results. **Retry applying saved results** retries a failed local publication without sending another provider request. Subtitle edits do not invalidate the frozen audio input or stop later audio requests.

## Credentials and dispatch

1. A native file dialog supplies the service-account JSON path to CredentialVault. Rust validates the format and fixed OAuth endpoint, then uses per-user Windows DPAPI. Settings display the JSON's project ID as read-only; import another JSON key to change it. Credential import takes effect immediately, and cancellation leaves the credential unchanged. Plaintext fallback is not supported.
2. The data directory has an exclusive process lock. Startup recovers interrupted dispatches as unknown outcomes and revokes stale execution approval. Unsent work requires renewed approval after restart.
3. Preparation hashes immutable inputs and body templates. Equivalent plans reuse the same job. A quote is valid for approval for 30 minutes; that is not a 30-minute execution limit for an already approved immutable plan.
4. SQLite reserves one request before dispatch. The ledger permits only one active request at a time. After authentication and input checks, dispatch validation rechecks approval, digest, cancellation, current limits, and the reservation before sending.
5. A valid response is saved and settled once. Completed requests cannot be resent. Pause and cancellation stop subsequent requests; they cannot revoke a request already being processed by Google.
6. Timeouts, interrupted connections, and unresolvable usage retain the appropriate hold and stop automatic progress. Acknowledging an unknown outcome does not refund it. Retrying requires a reviewed quote and separate approval.

The production transport uses fixed Google HTTPS endpoints with bounded responses, no redirects, and no hidden transport retries. The transcription worker handles explicitly approved HTTP 429 retries through the same durable reservation and dispatch checks as the original send. Other AI operations and the development validation CLI retain their existing single-attempt approval behavior.

### Transcription rate limits and retries

Transcription sends one request at a time, with at least 10 seconds between request starts. After an HTTP 429, this interval doubles to 20, 40 and then at most 60 seconds; three consecutive successful requests reduce it by 5 seconds, down to 10 seconds. The 429 cooldown also adds up to 20% jitter. Spacing and cooldown are stored per project/model/location and survive reapproval and restart; restart still requires approval. A response that already takes longer than the interval needs no extra pacing wait. This spacing adds no requests or approval allowance. The subtitle progress link and transcription workspace distinguish normal pacing from congestion recovery, show the next-send countdown, and retain pause/cancel controls and received subtitles. Only the native worker schedules requests; a countdown reaching zero does not dispatch from the UI.

An HTTP 429 response means the service is limiting requests or has insufficient capacity. During automatic retry, the subtitle progress link and transcription workspace show the affected chunk, retry count and wait time. The retry policy has base waits of 10 and 20 seconds with up to 20% jitter; the worker uses the later of that deadline and the adaptive congestion cooldown, so the first paced retry waits at least 20 seconds. A valid `Retry-After` header can extend that wait; it is never shortened. If the required wait exceeds five minutes, or the third send also returns 429, the job stops and shows why. A server-specified retry time continues to apply when reviewing the remaining work.

When both pacing and retry backoff apply, the later allowed send time wins. The UI gives automatic retry status precedence over ordinary pacing.

Retries resend the failed chunk from its beginning, using the same prepared audio and context overlap. Completed chunks are never resent. Pause and cancel also work during the wait. The worker rechecks approval, source identity and current limits immediately before each send. Restarting the app stops automatic execution and requires a new approval for the remaining work.

A 429 rejection is recorded separately from a lost connection or unknown response. It does not establish that the request was free: its monetary reservation or unpriced attempt remains in the accounting totals. A subsequent retry creates another reservation. The maximum priced reservation covers three sends per remaining chunk, including the initial send. Unpriced approval covers the corresponding maximum request count, audio duration and output limit without promising a dollar cap.

Older approvals do not gain automatic retries. An older 429 is explained as a rate-limit/capacity rejection, but its existing unknown-outcome record still requires acknowledgement before a fresh approval. Timeouts, disconnected requests, invalid usage and other HTTP errors are not automatically retried. No retry changes model or restores a revoked approval.

A valid usage record can settle a response whose content is rejected. Transcribe's STOP response may omit output-token count only when explicit input and total counts agree and other related counts are absent or zero. Other missing or invalid usage retains the hold.

## Prices and limits

Google Billing metadata is queried on request. Matching is conservative: ambiguous or incomplete prices remain unset. Users may enter their own input/output rates, including explicit zero rates. A snapshot records its source, observation time, and integer micro-USD rates. Changing the model or location in the editor clears the previous price for review. There is no built-in dated model/price catalog.

For priced jobs, each per-job, daily and monthly budget uses zero to mean unlimited. Positive limits remain enforced even when another limit is zero. Unlimited budgets still record reservations and usage. Input reservations use conservative byte/audio bounds; the configured output limit includes generated reasoning tokens. Usage settlement rounds upward in integer micro-USD. Cached input is conservatively counted at the supplied input rate. Prices and limits are an application accounting policy, not a provider-backed invoice cap.

Settings present the monthly budget as the main limit, with daily and per-job limits under detailed settings. Days and months use UTC calendar periods; one job can include multiple requests. Limits matching the monthly value follow changes to it; independently set values remain unchanged. Existing ledger limits are preserved. A zero value in any of the three limits leaves that limit unlimited.

For unpriced jobs, the user must explicitly approve the complete request count, submitted audio duration, and generation settings. A dollar ceiling cannot be calculated or guaranteed. Successful unpriced requests retain usage and a distinct uncalculated-cost state; they are not unknown network outcomes and are never represented as zero cost. The UI shows the calculated subtotal and the count of unpriced attempts separately.

Unknown priced reservations remain counted across UTC day/month boundaries. Known usage is attributed to the dispatch date. Costs from another device/application, taxes, future price changes, and billing adjustments are not controlled by this ledger. Reference: [Google pricing](https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing).

## Local audio preparation

The first explicit preparation downloads the pinned Silero model into app data, verifies its size and SHA-256, and uses the bundled CPU ONNX Runtime. This does not send media to Google. Tool leases retain the selected FFmpeg/ffprobe pair; executable hashes are checked before processing.

The chosen absolute audio-stream index is used for extraction. FFmpeg decodes the selected range once into mono 16 kHz PCM. Silero processes 512-sample windows with context and recurrent state. The same stream is written to temporary PCM, then exact sample ranges are encoded to FLAC. Memory does not grow with the complete audio length. Temporary PCM is removed after successful preparation; cancellation and errors terminate and reap child processes.

Chunks target 120 seconds, normally selecting pauses within 90–150 seconds and never exceeding 180 seconds. Pauses of at least 500 ms are preferred, then 200 ms pauses; forced boundaries remain possible. Each submission adds up to three seconds of context on either side. VAD does not delete audio or compress the timeline. Core intervals cover the original samples once, while send intervals deliberately overlap and are all counted in estimates.

The receipt binds sample intervals, source/stream identity, tools, VAD model, and generated audio hashes. Saved immutable audio can be reused without regenerating it. Changing the execution model can create a new quote for those inputs; changing source audio, selected stream, or prepared bytes invalidates reuse. Regenerated inputs require a new estimate.

## Transcript review and learning content

The parser retains the Transcribe text for each response part and validates its word anchors independently. Usable anchors produce timed cues. Missing, reversed, out-of-range or unaligned anchors produce a `source_block` row containing the original text and the exact submitted audio interval, including context. Those bounds identify source audio, not sentence or word timing. Source blocks remain available for reading, translation, explanations and cards, while synchronized captions, caption-group pause and SRT/VTT omit them. A card form permits an explicit audio subrange of at most 180 seconds inside a source block.

The review engine deduplicates shared word anchors only inside overlapping submissions. Repeated words at other times remain. A disagreement selects one candidate deterministically: the chunk owning that time, then the candidate farther from its submitted audio edge, then the smaller chunk ordinal. Original alternatives remain in the saved review. Missing responses stay pending; a valid empty response means that range was received and does not require a no-speech confirmation. Response corruption, timing-only failure and unknown usage are distinct states.

VAD assists local chunk boundaries. Whole-chunk no-speech and sustained-pause observations remain in detailed evidence for inspection; they neither suppress Transcribe text nor require acknowledgement before use. Pause evidence uses low-posterior Silero frames with its recorded guards and source ranges. It is an observation about the preparation, not a correction of the provider's transcript.

Each new job captures the current subtitle rows when its quote is created, independently of the frozen audio preparation. Approval activates that device-local publication session, which records expected full-row hashes, generated-row ownership, received coverage and protected intervals. Each publication commits subtitle changes and its session record together. Only unchanged existing rows in fully received coverage and unchanged generated rows can be replaced. A cue spanning an unreceived processing boundary stays whole until coverage is complete. Edits, translation changes, added/deleted rows and moved-cue intervals are protected; later candidates remain in the session. A newer approved request claims its interval from an older running job. The previous complete subtitle edition is saved once, and finishing a job records completion without replacing the complete list again.

Source audio, track and language verification remains separate from subtitle publication conflicts. Playback duration metadata updates do not detach publication; a selection beyond the current media duration cannot be published. Restoring an edition or importing another subtitle source detaches automatic publication for that media and stops remaining requests before their next dispatch. Learning restore clears publication authority and does not recreate it from old cloud output. Reopening a settled result or retrying a local publication never resends a completed provider request or changes saved cards.

Correct normal subtitles directly in the list while listening, or choose **Transcribe this range again** for a separately quoted request through the same workspace. Older saved jobs are recoverable from **Transcription history**: opening the history can locally reparse complete retained evidence, and **Use saved results** explicitly applies the available complete result. Existing job digests, approvals and charge records remain unchanged. The advanced range editor and [earlier draft-study bookmarks](draft-study.md) remain available for local recovery; authored empty ranges still require an explicit no-speech decision. See [transcript evidence](transcript-evidence.md) for the retained bindings.

Legacy manual range saving requires an inactive job and no in-flight reservation for that job. An unknown cost hold permits local authored correction while remaining reserved. Explicit application requires every range to have a valid effective result or manual revision and checks the current digest and source. Boundary alternatives and VAD observations are optional reviews. Applying through the same publication mechanism and recording adoption are local operations; adoption blocks further sending from that job.

Manual transcript-review revisions and publication sessions are device-local operational data, excluded from portable learning exports and cleared by learning restore. Provider evidence and the cost ledger remain separate. Phrase/subtitle editor drafts, applied generated subtitles and their timing precision are learning data in JSON/ZIP backups. The advanced boundary-repair API retains its separate, at-most-30-second quoted job and comparison alternative; it never creates an automatic paid fallback.

Vocabulary and explanation requests validate source cue IDs and selected text. Dictionary forms must preserve the same lexeme and semantic roles. A2/B1/C1 affect the frozen explanation request. Translation validates every source ID and checks source text, timing, language, and status again before local application. Quoted instructions remain translation data; URLs, code, JSON, and placeholders are preserved.

Cards use a consistent snapshot of the cited source text, complete source translation when available, and audio spanning the cited adjacent cues or the explicitly selected source-block subrange. Snapshots retain the original cue bounds and timing precision, while the card's source range records the chosen audio. A generated alternative example is labeled separately. Card audio and source snapshots are independent of later subtitle or media-cache edits.

## Development verification

The development-only [validation CLI](vertex-verification.md#build-and-initialize-the-cli) uses a separate data root and is excluded from application distribution. It supports explicitly approved requests and offline review of saved responses. The [test guide](testing.md) covers offline regressions and real FFmpeg, libmpv and Silero integration tests. Ordinary CI sends no Vertex requests.
